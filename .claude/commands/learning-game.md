`projects/security-quest/` と同じエンジン・同じ品質基準で、次の分野の学習ゲームを新しい作品として作ってください。

分野: $ARGUMENTS
（空欄なら、どの分野にするかだけ最初に質問する）

**目標**：全章をクリアすれば、その分野をほぼすべて理解できるレベルに到達すること。
知識だけでなく「状況を見て判断できる」ところまで届く問題にする。

## 先に読むもの（これ以外は必要になるまで開かない）

- `docs/decisions/0004-security-quest-structure.md` … 構成の決定と、問題の作り方のルール
- `projects/security-quest/app.js` … エンジン（コピー元）
- `projects/security-quest/data/ch01.js` … データ形式の見本（1章分だけ見れば十分）

## 手順

1. **カリキュラムを設計する。** 分野全体を4幕・15〜18章程度に分け、抜けている領域がないか確かめる。
   資格試験の出題範囲や標準的な教科書の目次と突き合わせ、範囲の根拠を最終報告に書く。
2. **作品ディレクトリを作る。** `projects/<英小文字ハイフンのslug>/` に
   `index.html` `app.js` `styles.css` `data/acts.js` `data/ch01.js`〜 を置く。
   `index.html` と `styles.css` は security-quest をコピーして、色とタイトルだけ分野に合わせる。
3. **app.js の分野固有の部分を必ず書き換える。** 残すと別作品の進捗が混ざったり、セキュリティの文言が出たりする。
   - `STORAGE_KEY`（例：`"<slug>-v1"`）。**全作品が同じオリジンなので、同じ値だと進捗が混ざる**
   - `SAVE_PREFIX`（例：`"ST1."`）と、読み込み欄のプレースホルダ
   - 称号（`RANKS`・`FINAL_RANK`）、ホームの導入文（`hero-lead`）、最終ボス名（`startFinal`）
   - 遊び方の「このゲームで届く範囲」、修了証の参考リンク（`resource(...)`。実在する一次情報だけ）
   - `grep -n 'セキュリティ\|ハコニワ\|security' projects/<slug>/app.js` で取り残しがないか確認する
4. **章データを書く。** 1章あたり講義カード5〜7枚、問題10〜14問、用語10〜20語。
   講義は「なぜそうなるか」まで説明し、問題は暗記の確認だけでなく事例で判断させる。
5. **検査する。** `node tools/check-learning-game.js <slug>` で、形式エラー0件・「正解が最長」が30%未満になるまで直す。
6. **ブラウザで確認する。** Chromium（Playwright）で全章を自動プレイし、次を確かめる。
   - 正解が正解・不正解が不正解と判定される（全問題形式）
   - 敗北、復習ダンジョン、最終試験、修了証まで通る
   - 375px幅で横スクロールが出ない、コンソールエラー0件
7. **ポートフォリオに組み込む。** 作品カード（サムネイル 1280×800 を `.jpg` と `.webp` で）、`sitemap.xml`、
   `docs/context/architecture.md` の作品表を更新し、`docs/decisions/` に決定を1件追加する。
8. ブランチを切ってコミット・push する。**`main` への push は必ず確認を取ってから。**

## 問題の品質ルール（最重要）

security-quest の初版は、選択問題の78%で正解が一番長く、内容を知らなくてもクリアできてしまった。同じ失敗をしない。

- 誤答は「明らかなハズレ」ではなく、**その分野の学習者が実際に抱きがちな誤解**で作る
- 正解だけに条件や但し書きを丁寧に書き込まない。4つの選択肢の長さと書きぶりを揃える
- 複数選択の正解数は「1つ」から「全部」まで散らす（「5つ中4つ」ばかりにしない）
- 誤答が見方によっては正解にもなる問題は作らない。迷ったら選択肢を差し替える
- 解説には「なぜ正解か」に加えて、よく選ばれる誤答が「なぜ違うか」を書く
- 問題を足すときは各章の `quiz` 配列の**末尾**に（途中に挿すと問題IDがずれ、復習リストが別問題を指す）

## 内容の正確さ

- 推測を事実として書かない。自信のない数値・年号・条文は、確かめてから使うか問題にしない
- 法改正・規格改訂など時間で変わる内容は、最終報告に「公開前に確認が必要な項目」として列挙する
- 実技を伴う分野では、クイズで届くのは「知識と判断の地図」までだと遊び方ページに正直に書く
