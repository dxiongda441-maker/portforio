# 記憶の仕組み — 使い方

このリポジトリが「会話の記憶」をどう保持しているか、と、どう運用するか。

## なぜ必要か

Claude の記憶は 3 層あり、放っておくと 2 つが失われる。

| 層 | 保持されるもの | 失われ方 |
|---|---|---|
| セッション内 | 会話の全文 | 長くなると自動要約され、細部が消える |
| セッション間 | **何も残らない** | 新しいセッションは前回を知らない |
| リポジトリ | ファイルの中身 | ✅ 残る |

Claude Code on the web ではコンテナごと破棄されるため、
**git に commit & push したものだけが次回に引き継がれる。**

## どこに何を書くか

```
CLAUDE.md              索引 + 常に守るルール。セッション開始時に自動で読まれる
docs/
├── memory-guide.md    このファイル
├── context/           「今どうなっているか」— 事実
│   ├── architecture.md
│   └── conventions.md
├── decisions/         「なぜそうしたか」— 判断の履歴
│   ├── TEMPLATE.md
│   └── NNNN-*.md
└── obsidian/          Obsidian Vault との連携
```

判断に迷ったら、この 1 行で決まる。

> **事実は `context/`、理由は `decisions/`、索引は `CLAUDE.md`。**

## 3 つの原則

### 1. CLAUDE.md は薄く保つ

毎回のセッションで自動的にコンテキストを消費する唯一のファイル。
肥大すると、毎回の会話で使える容量が減り、かえって精度が落ちる。

**目安は 60〜70 行**。ここに置いてよいのは次の 3 つだけ。

| 置いてよいもの | 理由 |
|---|---|
| 索引（どこに何があるか） | これが無いと `docs/` に辿り着けない |
| 個人設定（進め方・説明の粒度） | 毎回の振る舞いに効くので常時必要 |
| 忘れると事故になるルール | 例: PWA の `CACHE_NAME`。事後に気づいても遅い |

裏を返すと、**「調べれば分かること」は全部 `docs/` に置く。**
構成の詳細、判断の経緯、手順書はここに書かない。

### 2. 詳細はオンデマンドで取りに行かせる

`docs/` 以下は自動では読まれない。それでいい。
必要になったときだけ Claude が `grep` で探す。

```
「この構成にした理由を docs/decisions/ から探して」
「認証まわりの過去の判断ある？ docs/ を grep して」
```

### 3. 捨てた案こそ書く

「採用した案」は成果物を見れば分かる。
**「検討して捨てた案とその理由」は、書かなければ完全に消える。**
そして数週間後に同じ検討をやり直すことになる。

## 日々の運用

**判断したとき** — `/decide` を実行すると、会話から決定ログの下書きが作られる。

**セッションの終わり** — 残したいことがあれば:
```
今回の内容で docs/ を更新して
```

**その場でルールを足したいとき** — `#` で始めて発言すると CLAUDE.md に追記される。
```
# トップページの変更前は必ず差分を見せて
```

**セッションの始まり** — CLAUDE.md は自動で読まれる。それ以上が必要なら:
```
docs/context/architecture.md を読んでから始めて
```

## メンテナンス

- `docs/context/` は**事実**なので、古くなったら書き換える（履歴は git が持つ）
- `docs/decisions/` は**履歴**なので、書き換えず追記する。
  古い決定を覆すときは新しい番号で作り、古い方の状態を「置き換え済み（→ NNNN）」にする
- 月に一度、`CLAUDE.md` が膨らんでいないか見る。膨らんでいたら `docs/` に移す
